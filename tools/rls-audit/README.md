# tools/rls-audit — تدقيق رقي المباشر

أداة تشغَّل مرّة واحدة (أو ضمن CI) لتُثبت **آلياً** أن رقي يعزل بيانات كل مدرسة،
وأن الباغَين المعروفَين في حالتهما الفعلية، وأين استعلاماتك البطيئة. مخرَجها تقرير
واضح (`REPORT.md`) — هو بالضبط ما يقلب جلسة الوزارة من «ثقوا فينا» إلى «تفضّلوا، البرهان آلي».

## ماذا تفحص

1. **عزل المستأجر (RLS):** ينشئ مديريةً + مدرستين (A وB) تحتها + مدير مدرسة لكلٍّ،
   ثمّ يجعل مدير A يحاول `SELECT/UPDATE/INSERT/DELETE` على بيانات B عبر مسار
   المتصفّح نفسه. كل محاولة تُطبع: **✓ رُفِضت** أم **✗ تسرّبت**. يشمل ضابطاً موجباً
   (قراءة A لبياناته يجب أن تنجح) حتى لا يُخدَع بنتيجة «كله آمن» زائفة.
2. **الباغ #1 (notificationclick):** يُعيد بناء الرابط الذي يُنتجه `send-push`+الـSW
   لكل إشعار حقيقي، ويكشف أي مسار مطلق يسبّب 404.
3. **الباغ #2 (اشتراكات Push):** يحسب لكل دور كم مستخدماً يملك اشتراك Push فعلاً —
   ويعلّم المديرية/الوزارة بالأحمر إن كانت صفراً.
4. **الأداء:** أبطأ الاستعلامات (`pg_stat_statements`)، الجداول المَمسوحة تسلسلياً،
   الفهارس الناقصة على أعمدة العزل، و`EXPLAIN ANALYZE` لأثقل مسار تجميعي.

## التشغيل

```bash
cd tools/rls-audit
npm install
cp .env.example .env      # ثمّ عبّئ القيم من Supabase → Settings → API
npm run audit             # يشغّل الثلاثة ويكتب REPORT.md
```

أوامر مفردة:

```bash
npm run rls       # اختبار العزل (طريقة أساسية: بذر مستخدمين + PostgREST)
npm run rls:sql   # اختبار العزل (طريقة SQL بديلة: بلا بذر، آمنة/مُلغاة)
npm run bugs      # الباغان فقط (لا يبذر — يقرأ بياناتك الحيّة)
npm run perf      # الأداء فقط (يحتاج DATABASE_URL)
npm run teardown  # طوارئ: يمسح أي بيانات اختبار متبقّية
```

### طريقتان لاختبار RLS — ولماذا

- **الأساسية (`rls:` = `rls-test.mjs`):** تُنشئ مستخدمي auth حقيقيين وتسجّل الدخول
  بهم عبر مفتاح anon، فتُطبَّق RLS تماماً كما في المتصفّح. **لا تستعمل `ALTER ROLE`
  ولا `SET ROLE` إطلاقاً** — لذلك لا علاقة لها بخطأ «permission denied» الذي يظهر
  عند محاولة `ALTER ROLE`.
- **البديلة (`rls:sql` = `rls-sql-test.mjs`):** لِمن لا يريد إنشاء مستخدمين، أو
  اصطدم بقيود صلاحيات. داخل معاملة واحدة تستعمل **`SET LOCAL ROLE authenticated`**
  (وليس `ALTER ROLE` — الدور `postgres` عضو في `authenticated` فيُسمح به بلا
  superuser) + تضبط `request.jwt.claims` محلياً، فتُطبَّق RLS كأنك المستخدم. **كل
  شيء ضمن المعاملة ويُلغى بـ `ROLLBACK` — لا يُكتب حرف على الإنتاج.** تعمل بلا بذر
  على مستخدمَين حقيقيَّين من مدرستين.

> ⚠️ **ملاحظة مهمّة:** `service_role_key` **لا يصلح لاختبار RLS** — فهو يتجاوز RLS
> كلياً، فأي اختبار به سيبدو «آمناً» زوراً. نستعمله هنا للبذر/التنظيف فقط. اختبار
> RLS يجب أن يمرّ بهويّة مستخدم عادي (JWT) — وهذا ما تفعله الطريقتان أعلاه.

## الأمان — اقرأ قبل التشغيل

- **service_role يتجاوز كل RLS.** يُستعمل هنا للبذر/التنظيف/قراءة الحقيقة فقط،
  ولا يظهر في أي متصفّح. لا تدفع `.env` أبداً (محميّ بـ `.gitignore`).
- الأداة **تبذر ثمّ تنظّف** بياناتها (موسومة `__RLS_AUDIT__` وبريد `@ruqi-audit.test`).
  إن انقطع التشغيل، `npm run teardown` يمسح المتبقّي.
- تُنشئ مستخدمي auth حقيقيين مؤقّتين ثمّ تحذفهم. شغّلها على مشروع الاختبار/الحيّ
  بحذر خارج ساعات الذروة.
- اختبار RLS يكتب مؤقّتاً على صفوف مدرسة B للتحقّق، **ويسترجع القيمة الأصلية فوراً**
  عند اكتشاف أي تغيير.

## الدمج في CI (لاحقاً)

بعد التأكّد يدوياً، يمكن استدعاء `npm run rls` في وظيفة CI بأسرار GitHub، فيصبح
عزل المدارس مُبرهَناً عند **كل** دمج — لا «أمان بالصدفة».
